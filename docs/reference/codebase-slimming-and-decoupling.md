# 代码库瘦身与解耦：可追溯的参考依据

> 适用范围：对既有系统做行为保持的清理、去重、模块化和依赖方向修正。本文是参考材料，不是某一语言、框架或工具的强制规范。
>
> 访问日期：**2026-07-29**。除另有标注，链接均指向来源所有者的公开页面；文中的“综合建议”是基于来源和本仓库 `codebase-slimming` 工作流形成的工程综合，而非把建议误写成标准要求。

## 执行摘要

代码库“瘦身”的目标不是压低行数，而是在外部行为、业务规则、接口契约和数据兼容性可验证的前提下，减少重复、失控耦合、危险兼容分支和已证实无价值的实现。ISO 的产品质量模型公开元数据将模型用于指定、度量与评价，但公开页没有给出 LOC 目标，不能据此推出任何 LOC 阈值。[S1]

可维护的分解优先隐藏可能变化的设计决策，而不是仅按当前处理步骤拆文件；这来自 Parnas 对模块化的研究。[S2] 在工程执行中，低耦合和高内聚是有用的重构信号，但 .NET 的阈值检查、重复检测或静态可达性分析都只产生候选项，不能单独证明某段代码可删、两个实现可合并，或系统行为仍然正确。[S4][S7][S8]

因此，本参考采用以下次序：**只读扫描 → 是否值得继续的决策 → 行为基线 → 小范围试点 → 小批可回退的重构 → 自动化护栏**。这使“变小”从一个外观指标变成有证据的风险降低活动。

## 来源选择与核验方法

1. 优先使用标准机构、原始论文作者/出版者、平台维护者和工具维护者的公开页面；未使用搜索结果页、聚合 SEO 文章或不可核实的转载作为依据。
2. 将来源分为“规范性标准元数据”“研究/设计原则”“工程指导”“工具专用执行”四类。后面三类的建议不具备标准的强制性。
3. ISO/IEC 25010 的公开页面提供题名、版本、发布日期、适用范围和摘要，但标准全文并非免费公开；本文只把它作为**元数据与范围**依据，不声称其不可访问条款的细节。[S1]
4. GitHub 来源使用版本标签解析得到的提交固定链接，避免以会移动的分支作为证据。[S10]
5. 14 条外部 URL 均在交付时以 HTTP `GET` 跟随重定向检查：11 条返回 `200`；两个 ISO 页面及 ACM DOI 在自动化请求中返回 `403`，另经来源检索确认公开落地页或出版记录存在。此结果只说明访问日的可验证状态，不保证将来 URL、产品版本或页面内容不变。

## 注释式发现

### 1. 质量模型与指标：用来观察和排序，不用来替代目标

- **规范性标准元数据。** ISO/IEC 25010:2023 说明其产品质量模型由质量特性及子特性组成，可用于生命周期中的质量需求、评价、测试目标、验收准则和度量。由此可把可维护性、模块化风险与验证能力列入治理目标，而不是只统计源文件大小。[S1]
- **规范性标准元数据。** ISO/IEC 5055:2021 的公开摘要说明，其自动化源代码质量度量来自对架构和编码实践违规的检测与计数，关注这些违规可能造成的运行风险或过高成本。公开页同时显示该版正处于定期复审阶段；落地页不展示 235 页正文，因此本文不转述公开摘要之外的度量算法或阈值。[S14]
- **工具专用证据。** .NET 的 CA1505 将可维护性指数建立在 LOC、程序体积和圈复杂度之上；阈值可配置，也允许在仍被判断为可维护时抑制。这说明 LOC 是复合信号中的一个输入，不能成为删代码、删测试或压缩格式的唯一目标。[S5]
- **综合建议。** 分开记录生产、测试、生成物和第三方代码；用“关键行为仍通过、重复/复杂度/耦合热点下降、边界更清楚、回退更容易”作为主指标，LOC 仅作为辅助趋势。对数字设阈值前先记录基线、排除范围和业务风险。

### 2. 分解、信息隐藏、耦合与内聚

- **研究原则。** Parnas 比较了不同模块分解方式，讨论模块化如何改善灵活性与可理解性；其关键思路是围绕可能变化的设计决策来隐藏信息，而非只按执行流程切分。[S2]
- **工程/工具指导。** CA1506 以唯一类型引用数度量类耦合，指出高耦合实体可能难维护，并把低耦合、高内聚作为良好实践；其默认阈值可调，且适用对象是 C# / Visual Basic 符号。[S4]
- **综合建议。** 先问“哪些数据表示、存储方式、外部协议、业务规则会独立变化”，再定义接口和拥有者。相似代码只有在行为、变化方向、依赖方向、错误/事务语义都相同且新抽象可清楚命名时才合并；否则把它列为“有意重复”。

### 3. 依赖反转与稳定依赖方向

- **工程指导。** Microsoft 的 .NET 架构资料将依赖反转用于把基础设施与其他层解耦；在其 Clean Architecture 说明中，业务逻辑和应用模型居中，基础设施及实现细节依赖应用核心，而不是反向依赖。[S3]
- **综合建议。** 让稳定的业务策略拥有端口/抽象，让数据库、消息、HTTP、文件和第三方 SDK 适配这些端口；组合根负责接线。不要为“形式上的 DI”把每个小函数都抽象化；只在替换性、测试隔离、外部副作用或依赖方向确有需求时引入边界。

### 4. 小步、可逆的重构与行为基线

- **原作者工程指导。** Fowler 将重构描述为一系列小的、保持行为的转换；小步可降低引入错误的风险，并使系统在长期调整中保持可工作。[S12]
- **平台工程指导。** Google 的工程实践把小变更定义为一个自包含、聚焦的概念变更，而不是按行数机械判断；它还建议把较大的重构与功能/缺陷变更分开，并让纯重构也受到测试覆盖。[S13]
- **平台工程指导。** Microsoft 将单元、集成和功能测试分层，建议以可失败的条件与关键业务路径为测试对象，而不是追逐覆盖率；其 Well-Architected 指导还要求先验证测试自身、让回归集包含最有价值且稳定的测试。[S6][S9]
- **综合建议。** 无基线不改核心路径。基线至少记录构建、已有测试、代表性 API/UI/CLI 场景、数据前后状态、外部系统替身或验收路径及已知缺陷。每个批次只做一个可描述的结构改变，先验证再继续；失败时缩小、修复或回退，而不是叠加更多重构。

### 5. 去重与死代码：候选发现不等于删除授权

- **工具专用证据。** PMD CPD 是复制粘贴检测器，能够定位重复块，并说明若重复块本应表达同一行为，后续重构需要在多个位置同步；它不判定两个块在业务、事务、性能或异常语义上相同。[S11]
- **平台工程指导。** .NET 的裁剪分析从已知入口沿编译期可见路径追踪；反射、运行时装载与动态依赖会使静态分析无法确定运行时访问目标。文档明确要求对动态模式谨慎处理，并在裁剪警告存在时充分测试。[S7][S8]
- **综合建议。** 将“未被搜索命中”“静态工具报未使用”“CPD 命中”均视为候选，不视为删除证明。删除前需检查公开/API 契约、配置名、反射/DI 扫描、序列化、插件、任务调度、脚本、生成代码和运行时日志；再由测试或受控验收覆盖实际场景。高风险路径（权限、财务、并发、数据迁移、外部幂等）需要更强的人工与环境证据。

### 6. 架构边界应可检查，而非只写在图里

- **工具专用证据。** ArchUnit 的维护者说明其可分析 Java 字节码、检查包/类、层、切片和循环依赖，并通过普通单元测试断言架构规则。[S10]
- **综合建议。** 把真正重要的边界写成自动检查：例如“领域层不得引用基础设施命名空间”“适配器不得反向依赖 UI”“禁止跨模块内部类型引用”。选择与技术栈匹配的工具；ArchUnit 只是 Java 示例，.NET 可采用编译器分析器、依赖图或架构测试库。规则先从少量高价值、低争议的禁止项开始，并保留有理由的例外审查机制。

## 分阶段行动清单（综合建议）

下表是对本仓库代码库瘦身工作流的可执行化整理。每个簇都有外部依据；其中“必须/停止”的措辞是本地工程控制建议，不是 ISO、ACM 或工具的原文要求。

| 阶段 | 操作与产物 | 通过条件 / 停止边界 | 依据 |
|---|---|---|---|
| 1. Scan（只读） | 标出生产/测试/生成/第三方范围；收集构建、测试、依赖、重复、复杂度与动态调用风险。 | 不改核心代码；输出候选和风险，而非删除清单。 | S1、S4、S5、S7、S11 |
| 2. Decide（决策） | 选择 `CONTINUE`、`PILOT_ONLY` 或 `STOP`，给出收益区间和验证缺口。 | 无可重复基线、规则无人确认、外部/数据行为不可验证或只能靠压缩行数达标时停止。 | S1、S6、S9、S12、S13 |
| 3. Baseline（基线） | 固化构建/测试命令、关键输入输出、DB/消息/API 断言、已知缺陷和回退路径。 | 关键路径能重复观察；测试自身稳定且断言意图明确。 | S6、S9、S12、S13 |
| 4. Pilot（试点） | 选边界清晰、非高危、可测的中等模块；先补最小行为测试，再一次只改一类重复或依赖。 | 构建、测试、关键验收与人工可读性审查均通过；未引入反向依赖。失败不得扩大。 | S2、S3、S6、S12、S13 |
| 5. Refactor（分批重构） | 识别→理解→包围→替换→对比→切换→验证→删除→记录；每批独立提交/可回退。 | 任何行为、契约、数据、幂等、权限、性能或可观测性回归即暂停、定位或回退。 | S7、S8、S12 |
| 6. Guard（护栏） | 将关键依赖方向、重复/复杂度热点和回归场景接入 CI/评审清单；记录例外理由与到期复审。 | 护栏实际运行但不以噪声淹没开发；规则作用于可验证的边界。 | S4、S9、S10、S11 |

### 每批最小证据包（综合建议）

1. 目标行为与不变项：包含接口、数据、错误、事务/幂等和外部副作用。
2. 改动前后命令及结果：构建、单元/集成/功能测试，以及适用的人工验收或数据对比。
3. 依赖方向变化：新增/移除的项目、包、命名空间或运行时依赖，并说明是否符合边界。
4. 删除/合并证据：静态候选来源、动态风险核查、覆盖场景与可回退提交。
5. 指标变化：生产与测试分开，并说明它只用于观察，不替代行为证据。

## 反模式与决策边界

| 反模式或信号 | 为什么不足 | 应做的决策 |
|---|---|---|
| “LOC 必须下降 X%” | LOC 是 CA1505 等复合指标的输入之一，且变更规模本身也不应只按行数机械判断。 | 改成质量/行为/风险的组合目标；允许为测试、适配器或显式错误处理增加代码。[S5][S6][S13] |
| “CPD 命中就抽象” | CPD 发现文本/令牌层面的重复，不能证明业务语义、变化方向或事务语义相同。 | 先比较不变项与差异；无法命名、会增加开关参数或跨边界依赖时保留重复。[S11] |
| “未被引用就删除” | 静态可达性会遗漏反射、插件、动态装载和其他运行时依赖。 | 先核查动态入口和配置，再以测试/受控验收验证；不确定则保留并标记候选。[S7][S8] |
| “全库重写一次到位” | 大范围同时改变使行为差异难定位，丢失小步重构的可诊断与可回退性。 | 先试点，保持绿测试、小批次和清楚的回退点。[S6][S12] |
| “架构图已经说明边界” | 没有可执行检查的约定会随日常改动漂移。 | 把少数关键禁止依赖编码为适配技术栈的自动化规则，并审查例外。[S3][S10] |
| “分析器阈值就是质量真相” | CA1505/CA1506 的阈值可配置，且允许在特定上下文抑制。 | 以热点排序和审查为用途；记录阈值理由、误报与抑制原因。[S4][S5] |

```text
结论：CONTINUE / PILOT_ONLY / STOP / PASS / PAUSE / ROLLBACK
不变项：<行为、契约、数据、错误、事务/幂等>
证据：<命令、测试、受控验收、日志或数据对比>

指标：<生产与测试分开；仅作趋势>
剩余风险与下一步：<未覆盖场景、人工确认、回退点>
```
