# AI 生成代码的责任与验证：在人工理解和自动化约束之间建立风险分层治理

## 摘要

围绕 AI 生成代码，常见争论被压缩成两个口号：一方主张开发者应逐行阅读，否则便没有真正承担责任；另一方主张既然机器可以生成代码，人应把精力从阅读实现转向测试、度量和验收。这个二分法掩盖了真正的问题：不同变更的失败后果、回退难度、可观测性和验证证据结构并不相同，因此不存在一种对所有代码都最优的阅读规则。本文以公开材料的事实核查为起点，区分事实、推论与规范性主张，提出 AI 代码治理的核心不应是在“逐行阅读”与“完全不读”之间选边，而应按风险组合人工理解与自动化约束。本文的中心立场是：人可以不必逐行阅读所有生成实现，却不能把规格、关键不变量、证据解释和发布责任外包给生成系统或单一测试管线。同源自动化检查仍能提供快速反馈；当预言机相对独立、覆盖相应失败模式且与部署环境相连时，它才更可能构成足以支持高风险放行的强证据。人工阅读也不是天然有效，只有聚焦规格歧义、边界、异常路径和高后果决策时，才更可能降低关键风险。基于此，本文提出一套待试点检验的风险分层治理假说，并回应“测试足以替代阅读”“阅读才是唯一负责方式”“风险分层会拖慢交付”等反方意见。

**关键词：** AI 生成代码；工程责任；验证预言机；代码审查；风险分层；发布治理

## 一、问题提出：争论的对象不应是一种姿势

AI 提高了代码文本的生产速度，却没有相应地消除软件失败的后果。Agent 可以快速产生大量文件、补齐表面一致的测试并给出看似完整的解释；但权限绕过、迁移丢数、并发重复扣款、错误回滚或生产监控失明，并不会因为文本由模型生成就变得无害。真正需要回答的不是“人是否还要读代码”，而是：谁能在故障发生前识别错误假设，谁有权判断证据是否足够，谁在用户受损后承担修复、解释和停止发布的责任。

这里必须先澄清三个层次。**事实**是可以由来源直接支持的经验材料，例如某位工程师表示自己阅读代码，或另一位工程师主张用多层测试与度量约束 Agent。**推论**是从这些材料导出的工程判断，例如代码阅读和自动化验证各自不能单独覆盖全部风险。**规范性主张**则回答组织应当怎么做，例如高风险变更必须有人对关键不变量和发布证据签字。三者混写，容易把个人偏好装扮成普遍规律，也容易把一个测试通过误说成责任已经转移。

本文的论证从一个简单前提出发：软件质量不是生成文本的属性，而是系统在预期与非预期条件下持续满足约束的属性。代码只是承载这些约束的一个媒介；测试、监控、回滚、权限、运行环境和人的决策都会影响实际结果。因此，本文建议把治理单位设为一次**可发布的变更**及其风险，而不是“是否读完每一行”的姿势。文中关于扣款、权限、迁移等场景均是用于检验推理的工程例子，不是事故样本或效果数据。

## 二、事实基础与证据边界

已核验材料显示，两种看似对立的实践确实存在。Mitchell Hashimoto 在有关 AI 工作流质量与不一致性的讨论中回答过 [“I read the code”](https://x.com/mitchellh/status/2072738025344565262)；但原帖并未说他对所有生成代码逐行阅读，也未提出一条普遍政策。其[个人文章](https://mitchellh.com/writing/my-ai-adoption-journey)和[公开访谈发布页](https://newsletter.pragmaticengineer.com/p/mitchell-hashimoto)还涉及任务拆分、规划、验证工具与人工审查节奏。Robert C. Martin 则公开表达过[不阅读 Agent 所写代码、而以多种约束形成 gauntlet](https://x.com/unclebobmartin/status/2080257779395154409)的当前策略；同时，他也公开反思过[并非每个任务都需要最大化测试组合](https://x.com/unclebobmartin/status/2072736888478175413)。这些材料足以说明存在两种不同的实践重心，却不足以证明任何一方已经给出适用于一切项目的定理。完整事实、来源层级和限定语见[《AI 辅助代码阅读与验证：公开信息核验》](ai-assisted-code-reading-and-verification.md)。

同一核验还给出两项重要限制。第一，Microsoft 的单元测试指导明确提醒覆盖率本身不能判定质量；Stryker 对变异分数的定义也表明，该指标只说明测试发现了多少有效变异，并不证明需求已经被完整表达。[Microsoft：单元测试最佳实践](https://learn.microsoft.com/en-us/dotnet/core/testing/unit-testing-best-practices)；[Stryker：变异状态与指标](https://stryker-mutator.io/docs/mutation-testing-elements/mutant-states-and-metrics/)。第二，Christine Lemmer-Webber 的文章借用 Ka-Ping Yee 的博士论文讨论短代码审查仍可能遗漏困难缺陷，这可支持“人工阅读也有盲区”，但不能推出“审查无价值”。本文**没有**把该 PDF 说成已经逐页复核，也不把其中的特定实验外推为所有语言、所有团队的统计结论。

更应避免把未充分核实的信息作为证据。Cindy Sridharan 的相关长引语未找到可定位的一手出处；Theo 视频的身份和主题可以确认，但其所谓“四层代码模型”的逐项文本没有可核验的公开字幕或逐字稿。它们最多可作为待进一步考察的讨论线索，不能承担本文的论证支点。这个克制不是形式主义：若治理论文自身用不可复核归因支撑结论，便在实践上重演了它所批评的“看起来合理就放行”。

本文不是四维模型的效果研究，也没有数据证明该模型是降低事故的必要或充分条件。后文模型是从责任不可外包、单一证据存在盲区以及变更风险不同这三个前提出发形成的**可审计治理假说**。它是否改善漏检率、交付周期或恢复能力，仍需团队通过试点、对照基线和事故回测加以验证。

## 三、两种立场的最强版本及其边界

### （一）“应阅读代码”的最强论证

阅读派最有力的主张并不是“每一行都神圣”，而是责任不能在不理解后果的情况下成立。实现中常含有测试名称未表达的前提：时区、空值、重试幂等性、序列化精度、缓存失效、权限继承、并发交错、异常吞没。若负责人既不理解这些关键路径，又不能解释为什么现有证据足以覆盖它们，那么测试绿灯只是系统对自身假设的自证。尤其当规格本身含混时，模型可能把模糊要求稳定地实现为错误行为；此时更多同源测试反而会更有效率地巩固错误。

这个论证的推理链是：责任要求能够说明；说明需要掌握关键假设；关键假设有时只存在于实现、接口边界或运行约束中；因此，对高后果或难回退变更，人工理解不能缺席。它并不必然推出“逐行阅读一切”。对几十个由脚手架生成、可编译且无业务差异的文件逐行审阅，可能把稀缺注意力从真正危险的授权分支、迁移脚本和回滚路径上移开。阅读是发现问题的一种手段，而非责任本身的唯一形式。

### （二）“以约束代替逐行阅读”的最强论证

自动化派最有力的主张也不是“人应盲信机器”，而是人类逐行审查存在吞吐与注意力上限，且难以稳定发现复杂交互缺陷。若系统拥有可执行规格、属性测试、独立验收、静态规则、变异测试、端到端行为检查、运行时监控和可验证回滚，那么人把时间投入到设计这些约束、检查失败信号和维护反馈循环，有望比逐行检查大量常规实现更可扩展。Clean Coders 所描述的多角色、测试和 QA 管线，正体现了把质量控制从单一代码阅读扩展为多种证据的思路。[Clean AI: Agentic Discipline, Episode 6](https://cleancoders.com/episode/agentic-discipline-6)

其推理链是：如果 AI 显著提高实现产出速度，人的逐行注意力便难以同比扩张；可自动重复的检查能够稳定覆盖一部分已表达行为；因此，治理需要考虑把部分阅读预算从低信息密度的实现细节移向规格、预言机与运行证据。这个结论同样有边界：自动化不是天然独立的。若 Agent 同时写生产代码、测试和断言，三者可能共享同一误解；若测试环境没有真实身份提供方、历史数据或网络故障，证据也无法证明生产表现；若没有观测和回退，发现错误时可能已来不及阻止伤害。约束可以提高置信度，不能自动产生正确的目标函数。

### （三）可兼容的结论

两派的冲突主要来自把不同层次的问题混为一谈。阅读派担心的是**理解与责任被外包**；自动化派反对的是**把人工逐行检查误当作唯一质量机制**。本文据此提出：人不需要成为每个生成语句的抄写审阅者，但仍应是规格、关键不变量、证据解释和发布决策的最终所有者。适当的问题因而不是“读或不读”，而是“在何种风险下，由谁理解什么，并用哪些相对独立的证据补足其盲区”。这是规范性综合，不是两位实践者共同认可的原话。

## 四、可审计治理假说：后果、可逆性、可观测性与预言机独立性

本文提出四维框架，并把它作为**可被反驳和校准的规范性建议**，而非经验定律。四个维度不是必要条件或充分条件，也没有预设固定权重；它们的价值在于迫使发布者显式说明风险与证据，并让后续事故能够反查当初的判断。

第一维是**失败后果**：错误可能造成的金额、隐私、生命安全、合规、客户信任和修复成本。后果越高，越不能仅凭方便取得的证据放行。第二维是**可逆性**：能否快速、完整且不丢失信息地撤回。可回滚的 UI 文案与不可逆的数据迁移，即使代码量相同，也不应获得相同审查强度。第三维是**可观测性**：错误能否在造成重大伤害前被可靠发现。若异常会被明确告警、请求可追踪、状态可比对，自动化和灰度证据较有价值；若损害隐蔽、滞后或不可测，则应在发布前投入更多人工推理和受控验证。第四维是**验证预言机独立性**：判定“对或错”的规则在多大程度上独立于待测实现及其生成过程。独立性是连续谱而非二元标签，应追问：实现和测试是否来自同一需求解释、同一模型或同一数据？断言能否发现规格本身的错误？证据是否经过真实接口与环境？法律规则、已人工核对的样例、真实设备、不同实现或独立验收通常提供不同的信息来源，但仍需审计它们是否共享同一错误假设。

四维用于形成“理解—自动化”组合的初步判断，而不是简单相加，也不是效果保证。本文的保守假说是：高后果、难逆转、难在伤害前观察或证据高度同源的变更，应提高人工理解与独立验证强度；相反，低后果、易回退、高可观测且证据来源较多元的探索任务，可以主要依靠自动运行与抽样审查。这里的“人工理解”至少包括四件事：能复述业务目标；能列出不可违反的状态约束；能解释测试或监控的适用范围；能在证据相互矛盾时停止发布。它不等于把所有辅助函数逐行朗读。

## 五、反方意见及回应

### 反方意见一：测试通过已经客观，阅读只是主观仪式

回应：测试结果的执行是客观的，测试**所表达的世界**未必客观。一个断言只能证明程序满足该断言，不能证明断言涵盖了用户权益、边界输入和故障模式。若同一个模型根据同一句模糊需求先写实现再写测试，得到的是一致性证据，未必是独立正确性证据。因而本文不贬低测试，而是要求把测试划分为同源验证与独立验证：前者适合快速反馈，后者承担放行的关键证据。对资金、权限、隐私和迁移，应优先增加来自业务规则、已核对样本、不同实现或真实表面的预言机，而不能以覆盖率阈值取代说明义务。

### 反方意见二：只要要求人工读代码，AI 的效率优势就会消失

回应：这个批评针对的是无差别逐行阅读，而非风险治理。效率的真正敌人不是必要理解，而是把同样的审阅强度浪费在不同后果的变更上。风险分层反而允许低风险样板代码以自动检查和抽样为主，把高级工程师的注意力集中在少数会改变权限、状态、数据和恢复能力的节点。更重要的是，未被及时发现的高后果错误会以事故、返工、审计和信任损失的形式吞噬节省下来的生成时间。治理的目标不是最大化生成行数，而是最大化在可接受风险下的有效交付。

### 反方意见三：人也会漏审，强调人类责任只是保守主义

回应：人会漏审恰恰是本文主张多元证据的理由，而不是取消责任的理由。人工阅读不应被神化为完美检测器；它可能发现规格冲突、异常语义和不合常理的组合，却不擅长重复穷举。自动测试擅长重复、规模和回归，却容易受错误预言机限制。当两类证据确实来自不同信息源时，其错误模式可能不同，组合才有机会减少共因失效；若二者共享同一错误规格或同一生成假设，则完全可能一起出错。责任也不是宣称“我看过所以没问题”，而是记录何人确认了什么不变量、哪些证据支持发布、还保留哪些已知风险，以及发现异常后谁有权暂停和回退。

### 反方意见四：风险分层必然变成填表官僚主义

回应：任何治理都可能退化为表格，但这是设计失败，不是分层原则的反证。模型应只要求能改变决策的最少问题：最坏后果是什么？能否完整回退？会在何处、何时发现错误？预言机在多大程度上独立？若四问的答案没有改变审查和验证动作，表格就应删除；若答案暴露一次“普通重构”实际包含不可逆迁移或权限变化，简短筛查便提供了升级审查的理由。轻量记录不是为制造审批，而是让发布决策可追溯、可复盘、可改进；它是否值得成本仍要用试点数据验证。

## 六、可执行的风险分层治理模型

以下模型是把四维判断转为发布要求的**组织政策原型**，不是经验证有效的行业标准。为避免任意打分，初始判级采用“先看部署范围，再按最高风险维度上调”的保守规则：不进入共享或生产环境的可丢弃任务从 L0 起；可完整回退且不处理敏感数据的内部变更从 L1 起；任何用户可见的生产变更至少为 L2；涉及资金、权限、隐私、并发状态、数据迁移，或任一维表现为高后果、难逆转、损害前难观察、放行证据高度同源时，至少升至 L3；生命安全、法定记录或适用监管制度的变更进入 L4，并以领域标准为准。出现多个维度冲突时取较高等级，不以平均分抵消红线。

| 等级 | 典型变更 | 人工必须拥有的内容 | 自动化与运行证据 | 阅读要求与发布动作 |
|---|---|---|---|---|
| L0 探索 | 本地一次性脚本、无敏感数据的原型 | 目的、输入输出边界、销毁条件 | 基本断言、资源和权限限制 | 可不逐行读；不得直接进入生产。 |
| L1 低风险 | 可完整回退的内部工具、样板重构 | 接口、外部副作用、回退方式 | 构建、静态检查、代表场景测试 | 阅读接口、异常和副作用；其余可抽样。 |
| L2 生产常规 | 用户可见功能、常规业务规则 | 验收标准、错误语义、指标和负责人 | 分层测试、独立验收样例、灰度监控、回滚演练 | 阅读关键路径与高风险差异；由发布人解释证据。 |
| L3 高后果 | 权限、资金、隐私、并发、数据迁移 | 不变量、威胁或失败模型、前后状态、恢复方案 | 独立预言机、事务/并发测试、安全检查、受控环境验证 | 人工设计与关键代码双重审查；变更前后均需可审计证据。 |
| L4 安全关键或受监管 | 生命安全、法定记录、重大基础设施 | 可追溯需求、职责分离、适格人员责任 | 适用标准要求的独立验证、环境/硬件与运营证据 | 按领域制度执行；社交媒体经验和一般测试不得替代合规流程。 |

判级由变更负责人提出，由实际承担发布风险的产品、数据、安全或领域责任人确认；L3 以上不应由生成实现或撰写测试的同一主体单独批准。争议未解决时按较高等级执行。确需例外时，应记录理由、剩余风险、批准人、有效期限和复审条件，使“临时放行”不会悄然变成永久豁免。不同组织可调整等级名称与门槛，但必须保留明确裁量者和可回溯依据。

为避免模型停留在分类，团队可把每次 L2 以上变更纳入一张简短的“责任卡”：

1. **规格与不变量。** 用可检查语言写明成功、拒绝和恢复条件；例如“同一订单在任意重试与并发交错下最多扣款一次”，而不是“避免重复扣款”。
2. **证据图。** 对每个不变量列出至少一种验证，以及其独立性：测试是否与实现同源、是否使用已核对数据、是否覆盖真实接口和失败路径。缺少独立证据时，明确标为剩余风险，而非用更多相似测试掩盖。
3. **阅读预算。** 指定必须人工理解的节点：授权决策、状态转换、序列化边界、迁移与回滚、并发原子性、外部副作用。生成的样板、可再生代码和纯展示细节可由自动检查与抽样覆盖。
4. **发布闸门。** 写明灰度范围、观测指标、告警阈值、停止条件和回退负责人。测试通过不是自动发布命令；它只是责任人判断是否跨越闸门的输入。
5. **事故闭环。** 任何漏检都要追问失败在哪一层：规格、预言机、实现、环境、监控还是决策，并把修正沉淀为新不变量或新证据，而不止于要求下次“更仔细读代码”。

这套原型应先在有限范围试点，而不是直接宣称有效。团队可以在试点前记录基线，并持续观察交付周期、人工审阅时间、发布后漏检缺陷、误阻断比例、回退成功率、平均恢复时间，以及关键断言来自多少相对独立的信息源；再用事故和近失事件回测四维判断是否遗漏了真正风险。若模型只增加表单而没有改变漏检、恢复或决策质量，就应删减或重设门槛。其待验证目标不是增加生成代码量或审查小时数，而是让高后果缺陷更有机会在伤害前被发现、让恢复更可靠，并让团队能够解释为什么当时允许发布。

## 七、结论

“逐行阅读”与“完全不读”都不足以单独构成 AI 代码治理原则。前者若不区分风险，可能把人力耗在低价值细节；后者若缺少相对独立的预言机和运行证据，可能把责任藏在自动化绿灯之后。本文据此形成的**推论**是，两种方法具有互补的可能；本文提出的**规范性假说**是，组织可以用失败后果、可逆性、可观测性和预言机独立性，决定人工理解、代码审查、自动化验证和发布控制的组合，并以试点数据检验这一组合是否实际改善结果。

最小但不可让渡的责任集合应始终留在人手中：拥有规格，确认关键不变量，解释证据的适用范围，并对发布、暂停与回退作出决定。AI 可以生成实现、测试和报告；它不能替代组织决定什么损害不可接受，也不能替代被授权的人在证据不足时说“暂不发布”。这套责任结构旨在让自动化扩大可靠交付能力；它能否做到，应由持续测量和失败复盘回答，而不能由本文的逻辑推演预先保证。
